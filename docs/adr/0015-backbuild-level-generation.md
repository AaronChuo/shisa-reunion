# ADR-0015：逆築——先搭出解，再反推關卡

- 狀態：已採用
- 日期：2026-10-18

## 背景

原本的關卡生成是「抽了再驗」：隨機抽地形和托盤積木，交給求解器窮舉，看有沒有解、解有幾個、是不是每塊都要用。實測時間約 99% 花在求解器上，而且抽出來的關卡約 95–99% 根本無解。要證明無解就得把所有擺法試完，地基越寬越慢，所以 v0.13 首里城只能停在 8 格（ADR-0014）。

接下來的新分區會帶回溜滑梯、石拱橋、漲潮，組合會變多，地基也想更寬，所以需要更有效率的生成方式。

## 決策

- **命名「逆築」**（英文 Backbuild，程式 `src/engine/backbuild.ts`）：先把路搭好，再把積木收回托盤
- **它是生成流程裡新增的搭路器，不是求解器的優化**。求解器的角色不變，仍然是裁判：
  1. `drawTerrain`：抽地形（主角、終點、固定積木、海膽、石門、星砂、漲潮）
  2. `backbuild`：從該區積木池一塊一塊挑積木和位置，讓路一步步接近終點（用「主角走得到的地方」和「走得到終點的地方」之間的距離當指標，在最好的幾個裡隨機選，避免每條路都一樣）
     - 不讓路提早接通，所以每塊都要用
     - 最後一塊試遍所有位置，挑一個能把路接通、而且符合該站要求（必要動作、穿過石門）的
     - 石門的話，第一塊先放上壓板
     - 搭好後，任拿掉一塊路都必須斷掉
  3. 用到的積木就是托盤；`judge` 交給求解器驗證公平，規則和以前完全一樣
- **混用，逆築為主**（`methodsFor`、`generate`）
  - 一般關卡先用逆築，連續失敗一段時間（700ms）就換成抽了再驗（250ms），輪流直到成功；再不行才照舊放寬條件
  - **有藤蔓的關卡只用抽了再驗**：藤蔓要掛在一塊「懸空、但被別的積木撐住」的積木下面，需要兩步以上的鋪陳，一塊一塊往前搭的方式找不到（實測已知有解的地形上 0/300）
- **量測工具**：`pnpm bench:gen` 用同樣的設定比較兩種方法的速度和關卡特徵（解的數量、路線長度、爬多高、用到幾種動作、幾種積木），之後改生成器都要跑

## 實測（全部 106 種元素組合，每種 3 個 seed）

| 類別 | 原本平均／最慢 | 逆築混用平均／最慢 |
| --- | --- | --- |
| 不含藤蔓 | 88／832 ms | 30／162 ms |
| 有石門（不含藤蔓） | 390／832 ms | 43／85 ms |
| 有藤蔓 | 不變，最慢約 1.8 秒 | |

寬地基（`pnpm bench:gen`）：10 格寬的石門關從約 1.5 秒降到約 0.15 秒一關；9 格寬的石拱橋、溜滑梯也快 1.5–2.5 倍。

關卡特徵兩種方法很接近；逆築的托盤積木種類略少（例如 2.5 對 2.9 種），混用正好保留多樣性。

## 影響

- 首里城、竹富島等有石門或星砂的關卡生成明顯變快；新分區可以考慮更寬的地基，只要那一區的組合沒有藤蔓
- 同一個 seed 仍然產生同一關（除非生成慢到換方法或放寬條件，跟以前一樣）
- 舊方法保留，是藤蔓關卡的主力，也是比較基準

## 之後

- **藤蔓的鋪陳**：讓逆築能預先架好藤蔓的掛點（例如先放跨欄的積木再掛藤蔓），之後藤蔓關卡也能換成逆築
- 托盤積木種類的多樣性可以再加權調整
- 求解器本身的效能（例如更快的格子表示法）是另一件事，需要時再做
